Control plane · admission · lifecycle

Harborbox

A durable queue and an admission controller in front of OpenSandbox. It decides whether a sandbox may run and when. OpenSandbox decides what a sandbox is.

The whole chain

client→Harborbox API→Postgres queue→scheduler→OpenSandbox→runtime
01

What the thing actually is

Harborbox is not a container runtime. It owns four things and delegates everything else: a PostgreSQL execution queue, an aggregate memory and CPU budget for the host, a scheduling policy, and a product-facing lifecycle API. Container creation, commands, files, snapshots and isolation belong to upstream OpenSandbox.

The split matters because it explains every design decision below. Harborbox never touches Docker. It writes rows, decides who goes next, and makes HTTP calls to OpenSandbox. That is the whole job.

The two background loops

Everything time-based happens in two asyncio loops inside the API process, both started in Scheduler.start().

  • The admission loop scans the queue and admits what fits. It is woken by a Postgres NOTIFY on enqueue, not by a clock. The scheduler_poll_seconds interval (0.25 s) survives only as a fallback timeout, so a lost notification costs latency, never a stall.
  • The reaper loop runs every 5 s and does three sweeps: kill expired sandboxes, walk idle ones down the pause ladder, and — rate-limited to once an hour — garbage-collect unused template images.

Two details in that animation are easy to miss and both are load-bearing.

Reservation starts at starting, not at running. The moment admission says yes, the scheduler flips the row and the memory is counted as spent. It reserves the sandbox's entire hard limit, not its current usage — a 1 GiB sandbox costs 1 GiB of budget whether it is running numpy or sleep.

A frozen sandbox still holds all of its memory. paused_memory is in RESERVED_SANDBOX_STATES; only paused_cold gives the memory back. That is why the hot tier has its own separate cap, HARBORBOX_HOT_PAUSE_BUDGET_MB — past it, idle sandboxes skip the freeze and go straight to snapshot.

Measured, not assumed

The timings in the animation come from tests/e2e_pause_ladder.py against a live stack at 256 MB / 0.5 CPU. Freezing costs 65 ms and snapshotting costs 5,075 ms — so the pause side is where the hot tier overwhelmingly pays. On the resume side it buys about 370 ms (97 ms unfreeze against 465 ms restore), which is a real win but a much narrower one than "sub-second versus seconds" suggests. Set HARBORBOX_HOT_PAUSE_IDLE_SECONDS=0 where memory is the binding constraint.

03

What happens when you run a command

The API never runs anything. POST /v1/sandboxes/{id}/commands writes a queued row and returns. Everything after that is the scheduler.

Four separate poll loops used to sit between a caller and its result. On a warm sandbox running trivial code, those intervals were most of the observed latency — the work itself was single-digit milliseconds. The LISTEN/NOTIFY pair replaced them. Nothing in it is load-bearing for correctness: every waiter still has a timeout, and every timeout degrades to exactly the polling behaviour it replaced.

04

How concurrency works

There are three different concurrency questions in this system and they are governed by three different mechanisms. Keeping them apart is most of understanding the scheduler.

  1. How many sandboxes may hold host resources — the admission controller, on memory and CPU. This is the interesting one.
  2. How many executions may run inside one sandbox — a flat count, HARBORBOX_MAX_CONCURRENT_EXECUTIONS_PER_SANDBOX. The container's own hard limits bound whatever they do.
  3. How many control-plane processes may exist — exactly one, today. More on that in section 07.

The admission test

Every queued execution is scanned in FIFO order. For each one, the scheduler asks what admitting it would add to the current reservations — nothing at all if its sandbox is already running — and applies three tests in order:

admission.py · can_admit
reserved_memory + requested_memory <= sandbox_budget_mb → else waiting_for: "memory" host_available_memory - requested_memory >= emergency_reserve → else waiting_for: "memory" reserved_cpu + requested_cpu <= max_parallel_cpu → else waiting_for: "cpu"

The second test is the emergency guard, and it is the only one that looks at the real machine rather than the ledger: it reads MemAvailable from /proc/meminfo live. Harborbox can stop its own queue from overcommitting, but it cannot stop unrelated processes from eating the host — this is the check that notices when they have.

FIFO, with backfilling, with aging

A strict queue wastes capacity: a 4 GiB job at the head blocks a 256 MB job behind it even when 512 MB is free. A pure best-fit queue starves the big job forever. Harborbox does both, switching between them on a timer:

  • Scan the queue in order. If a job does not fit, skip it and keep scanning — that is the backfill, and it is what keeps small work moving.
  • Unless the job that did not fit is at the head of the queue and has waited longer than HARBORBOX_QUEUE_AGING_SECONDS (60 s). Then the scan stops dead. Nothing behind it is admitted until it goes.

So the queue is opportunistic for the first minute of any job's wait and strictly first-come after that. One sweep looks at scheduler_scan_limit = 100 rows.

Inside the process

Admitted executions become independent asyncio tasks. Two of them landing on the same cold sandbox at once would happily create two containers, so every start goes through a per-sandbox asyncio.Lock; whichever task loses the race re-reads running from the database and does nothing. A caller that gives up waiting does not cancel the start — it is asyncio.shielded, because aborting mid-start_sandbox would strand a container the row never learns about.

05

Where the limits come from

The memory ceiling is not one number. It is the smallest of several, computed fresh on every sweep:

Capacity.sandbox_budget_mb
host_budget = host_total_memory - max(RESERVE_MIN_MB, host_total × RESERVE_PERCENT / 100) - PLATFORM_MEMORY_RESERVE_MB budget = min(host_budget, SANDBOX_MEMORY_BUDGET_MB)

host_total_memory is MemTotal from /proc/meminfo — inside the API container, so on Docker Desktop or OrbStack it is the Linux VM's memory, not the Mac's. Cap that VM below physical RAM (50–65% is a reasonable start) and Harborbox then holds back a further 25% of it.

The two shipped answers

On the bundled Compose stack, with a 16 GiB Docker VM and nothing overridden:

  • Sandboxes on the base template (512 MB / 1.0 CPU): three at a time. Memory would allow seven; CPU allows three, because the warm pool permanently holds 1.0 of the 4.0 allotment. A fourth container exists — the warm one — but it is idle and holds no CPU.
  • Sandboxes on a custom template with no explicit sizing (1024 MB / 2.0 CPU): one at a time. Memory would allow three. CPU allows one. Everything else queues.

If that second number is a surprise, it is the honest one, and it is the number worth acting on: MAX_PARALLEL_CPU=4 against a 2-CPU default sandbox size is a tight pairing. Raising HARBORBOX_MAX_PARALLEL_CPU to the host's real core count, or sizing sandboxes at 1.0 CPU, is what moves it.

Three counts that are not that one

  • Sandboxes that exist is far larger. paused_cold holds no memory and no CPU, so cold-suspended sandboxes are bounded only by row retention. Cold-start each one back and they queue.
  • Sandboxes holding memory sits between the two: running plus starting plus paused_memory plus the pool. Frozen sandboxes count against the memory budget but not the CPU one.
  • Concurrent executions is the running count multiplied by MAX_CONCURRENT_EXECUTIONS_PER_SANDBOX. A second command into an already-running sandbox costs nothing in admission — its incremental memory and CPU are both zero — so it is gated only by that per-sandbox limit.

GET /v1/capacity reports all of it live: budget, reservations, warm-pool headroom, running sandboxes, running and queued executions.

07

Kubernetes, and multiple deployments

You are right that OpenSandbox has a Kubernetes backend, and Harborbox is already positioned to use it — but "use the K8s runtime" and "run Harborbox across multiple systems" are two separate changes, and only the first one is free today.

works now

Pointing at a Kubernetes OpenSandbox

Harborbox reaches OpenSandbox over plain HTTP through HARBORBOX_OPENSANDBOX_DOMAIN, _PROTOCOL and _API_KEY. Nothing in the control plane assumes a local runtime, and the SandboxRuntime protocol exists precisely so that a different provider is an addition rather than a change to the scheduler, admission or API. This is also the repo's own recommendation for hostile workloads — Docker containers share the host kernel, so gVisor, Kata or Firecracker behind a RuntimeClass is the isolation story, not this.

works now

Shared state across instances

Two of the hard parts are already done. Warm pools coordinate through PostgreSQL with distributed leases and leader fencing (postgres_pool_store.py), and the wake-up path uses LISTEN/NOTIFY on that same database specifically so it reaches every API replica without adding a broker. Both were written for more than one process.

blocked

More than one Harborbox process

The single-start guarantee is an in-process asyncio.Lock dictionary. Two replicas against one database hold two unrelated lock dicts, race the same sandbox row, and can produce two containers for one sandbox. Dockerfile.api's uvicorn has no --workers for exactly this reason. The fix is known and small in shape — a SELECT … FOR UPDATE on the sandbox row, the same pattern admission already uses — but it is not written.

blocked

Admission across more than one machine

Capacity is a single global budget measured from the API container's own /proc/meminfo. HARBORBOX_TOTAL_MEMORY_MB can override the total, but the live emergency guard still reads local MemAvailable — on a split deployment it is watching a machine that runs nothing. And a single flat budget cannot express per-node capacity, so against a cluster you would have two schedulers bin-packing the same workload with different information. Multi-node needs capacity to come from the runtime rather than from /proc.

needs work

The template registry address

BuildKit pushes to registry:5000 over the build network; the reference handed to OpenSandbox is 127.0.0.1:5050, because the Docker daemon resolves it from the host. That pairing only holds while OpenSandbox is on the same host. A split or clustered deployment needs a real DNS name with TLS — the design doc already calls this out as the option for exactly this case.

The short version

Harborbox can run on top of Kubernetes today: point it at a clustered OpenSandbox, set HARBORBOX_TOTAL_MEMORY_MB deliberately, give the registry a real name, and accept that one API process is scheduling the whole cluster from a budget you typed in rather than measured.

Harborbox cannot yet be a multi-instance deployment. Three things stand between here and there, in dependency order: replace the in-process start lock with a row lock; source capacity from the runtime instead of local /proc; then decide whether Harborbox still schedules at all once Kubernetes is doing it — because at that point one of the two schedulers is redundant, and the interesting question becomes whether Harborbox keeps the queue and admission and hands placement to the cluster, or steps back to being the durable queue and lifecycle API alone.

That last question is a design decision, not a missing feature, and it is worth settling before the other two are built.
